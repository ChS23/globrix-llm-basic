# Globrix — Итоговая архитектура мультиагентной системы

Globrix — это система, в которой один диалоговый агент ведёт работу с риэлтором, а GenUI-агент управляет состоянием интерфейса сделки через JSON, действуя как инструмент.

Вся логика взаимодействия, поиска объектов и обновления UI строится вокруг этой двухагентной схемы.

---

## 1. Главный агент (Realtor Agent)

Единственный агент, который взаимодействует с человеком.

Он выполняет три роли:

### A. Диалоговый агент

- понимает запросы риэлтора;
- отвечает в естественном языке;
- ведёт пользователя сквозь процесс работы со сделкой.

### B. Orchestrator (управляющий агент)

- принимает решения, какой инструмент вызвать;
- когда обновлять интерфейс;
- какие данные нужно загрузить;
- какие проверки или пояснения дать;
- что именно должен изменить GenUI.

### C. Управление данными и доменными справками

Он вызывает:
- **SearchProjectTool** (поиск проектов по названию)
- **FetchApartmentsTool**
- **FetchVillasTool**
- **RegionalRAGTool** (юридические и региональные справки)

> Главный агент не хранит и не модифицирует JSON-состояние страницы.
> Он лишь описывает, что должно быть изменено.

---

## 2. GenUI Agent (Agent-as-a-Tool)

GenUI — это полноценный агент, но работающий как инструмент главного агента.

Он выполняет только одну функцию:

**Трансформация JSON-состояния интерфейса сделки.**

### GenUI делает:

**Чтение текущего состояния**
- `GET /deal/{id}/state`

**Применение инструкции главного агента**
- корректировка блоков, данных, структуры

**Запись обновлённого состояния**
- `POST /deal/{id}/state`

> GenUI не ведёт диалогов, не принимает решений,
> он — исполнитель сложных UI-изменений.

---

## 3. Deal API

Центральный слой хранения состояния:

- создаёт сделки;
- хранит JSON-структуру страницы;
- отдаёт её фронтенду;
- принимает обновления от GenUI.

### Формат состояния (пример):

```json
{
  "deal_id": "abc123",
  "blocks": [
    {
      "type": "project_list",
      "props": {
        "projects": [ ... ]
      }
    },
    {
      "type": "apartment_cards",
      "props": {
        "items": [ ... ]
      }
    }
  ]
}
```

> Frontend полностью детерминирован:
> он только рендерит массив блоков.

---

## 4. Инструменты (Tools) главного агента

### Поиск:
- **SearchProjectTool**
- **FetchApartmentsTool**
- **FetchVillasTool**

### Инфраструктура:
- **RegionalRAGTool** (юридические/региональные справки)

### UI:
- **GenUIAgentTool** (полный доступ к JSON-состоянию UI)

> Тулзы выполняют узкие функции, без reasoning.

---

## 5. Поток данных (основной сценарий)

```
Пользователь
    │
    ▼
Главный агент
    │ анализ запроса
    │ вызов инструментов (поиск / выгрузка / RAG)
    ▼
GenUI Agent (как Tool)
    │ читает JSON
    │ модифицирует блоки
    │ сохраняет новое состояние
    ▼
Deal API
    │ отдаёт состояние
    ▼
Frontend рендерит новую страницу
```

---

## 6. Принципы системы

- **2 агента** → минимальная сложность
- **LLM принимает решения**, но не строит UI вручную
- **UI полностью управляется JSON состоянием**
- **Фронт рендерит фиксированный набор блоков**
- **Региональная экспертиза через RAG**
- **Поиск объектов через простые, стабильные тулзы**
- **Строгое разделение ответственности:**
  - главное мышление — в Главном агенте
  - модификации страницы — в GenUI

---

## 7. Стратегическое достоинство подхода

| Аспект | Описание |
|--------|----------|
| **Масштабируемость** | легко добавлять новые UI-блоки и операции |
| **Надёжность** | UI не «генерируется», а собирается из стабильных компонентов |
| **Простота формальных проверок** | JSON состояние всегда валидно |
| **Разделение мышления и действий** | классический принцип Multi-Agent Alignment |
| **MVP готов быстро** | достаточно определить JSON Schema и 5–7 блоков |

## 8. Региональный RAG (Regional Knowledge Layer)

Региональный RAG — это специализированный контур знаний, который обеспечивает систему локальными юридическими, инфраструктурными и рыночными данными.

Он функционирует как доменно-ориентированный справочный слой для главного агента.

### 8.1. Роль в архитектуре

**Задача RAG:**
Давать главному агенту точные и проверяемые ответы, относящиеся к локальному рынку недвижимости.

Главный агент использует его для:
- объяснений (права, ограничения, условия);
- интерпретации терминов;
- локализации проектов;
- оценки инфраструктурных преимуществ;
- предоставления точной справочной информации риэлтору.

> RAG не генерирует UI и не модифицирует state.
> Он — справочник и источник знаний.

### 8.2. Какие данные входят в RAG

#### 1. Юридические данные
- правила приобретения апартаментов и вилл;
- ограничения на владение для нерезидентов;
- особенности субаренды;
- региональные налоговые режимы;
- HOA / Maintenance Fee / Service Charge.

#### 2. Зонирование и инфраструктура
- карта инфраструктуры;
- близость к аэропортам, школам, больницам;
- транспортная доступность;
- ограничения застройки.

#### 3. Терминология рынка
- типы сертификатов;
- термины, связанные с Developer Approval;
- escrow;
- handover;
- DLD fees и др.

#### 4. Данные по проектам и районам
- районы Дубая;
- известные застройщики;
- популярные проекты и их специфика.

### 8.3. Архитектура RAG

RAG состоит из трёх уровней:

**A) Индекс (Vector Store / Elastic)**

Хранит:
- региональные документы;
- юридические справки;
- описания районов;
- словари терминов.

**B) Реранкер**

Повышает точность выдачи.
(на основе cross-encoder / monoT5 / biencoder reranking)

**C) Synthesizer**

Формирует короткие, точные ответы.
Формат отдачи → предназначен для главного агента.

### 8.4. Как главный агент работает с RAG

**Поток:**

1. Главный агент видит, что вопрос содержит термин, юр. контекст или региональную инфу.

2. Он вызывает **RegionalRAGTool**.

3. Тулза:
   - извлекает контекст,
   - реранкует,
   - формирует краткую справку.

4. Агент использует ответ RAG → формирует человеческое объяснение для риэлтора.

> RAG не знает о UI.
> RAG не знает о сделках.
> RAG не знает о JSON состоянии.
>
> Только знания → Агент → Человек.

### 8.5. Почему RAG обязателен

| Причина | Описание |
|---------|----------|
| **Стандартизация терминов** | В недвижимости огромное количество специфических терминов. Агенту нужен стабильный источник правды. |
| **Локализация запросов** | Запросы всегда привязаны к региону (например, Дубай). |
| **Юридическая корректность** | Пояснения без ошибок — обязательное требование. |
| **Персональная адаптация ответа** | Агент может учитывать район, объект, проект. |
| **Обоснованность** | RAG даёт проверяемый контекст. |

## Итог: три столпа архитектуры Globrix

```
           Пользователь
               │
               ▼
     Главный агент (диалог + мышление)
               │
               ├── Tools (поиск, выгрузка, RAG)
               │
               └── вызов → GenUI Agent (как Tool)
                       │
                       ▼
                   Deal API
                       │
                       ▼
                   Frontend UI
```

| Компонент | Роль |
|-----------|------|
| **Главный агент** | даёт смысл |
| **GenUI** | меняет состояние UI |
| **RAG** | даёт знание |
| **Deal API** | хранит JSON страницы |
| **Frontend** | рендерит UI |
